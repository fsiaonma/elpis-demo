# Part4 · Resume Studio — 规格说明（spec）

> 回答「做成什么样」。实施顺序与验收口径见 [plan.md](./plan.md)；任务排期见 [tasks.md](./tasks.md)。

---

## 1. 目标与用户故事

**目标：** 把「上传一份简历 → 得到可审计的分析报告 + Top 10 岗位推荐」做成 elpis 框架上的可发布产品 **Resume Studio**（项目代号 `war-room`）。

**一句话用户故事：**

> 给我一份简历，告诉我它强在哪、弱在哪，以及库里哪十个岗位最值得投。

---

## 2. 客户与真痛点

| 表层说法 | 真问题 |
|----------|--------|
| 「改简历太费时间」 | 「人工判断不可复用」—— 同一份简历、同一批 JD，不同顾问给出的强弱项与排序不一致，且无法追溯依据 |

Part4 不承诺「替用户改好简历」，而是把 **可复用的判定链路** 产品化：每条分数有 rubric 出处 + 简历原文证据，综合分由规则引擎可审计地算出。

---

## 3. 产品边界

- **不替代人：** 模型与规则只产出结构化判定与排序建议；最终「投不投、怎么改」留给用户。
- **时效目标：** 把一次人工初筛从约 **40 分钟** 压到约 **10 分钟**（含上传、等待分析、阅读报告）。
- **范围外：** 不做在线简历编辑器、不做投递跟踪、不做 HR 侧 ATS、不做自动代投。

---

## 4. 交付的产品

Resume Studio 交付 **三个页面能力**（均挂在 `war-room` 项目 model 下，详见 [plan.md § 页面策略](./plan.md#页面策略)）：

### 4.1 简历库（schema 驱动列表）

- 数据来源：MySQL `zteam.t_resume`（schema 配置驱动 CRUD）。
- 原文件落盘：`data/resumes/`（不进 git，见 [plan.md § 状态落点](./plan.md#状态落点)）。
- **分析入口：** 列表行操作「分析」→ 跳转分析报告页并触发编排链路。

### 4.2 岗位库（schema 驱动 · 只读列表）

- 数据来源：MySQL `zteam.t_job`；种子 **150–300 条** 岗位由 SQL 导入，不在页面上录入。
- 列表字段（只读）：**标题 / 公司 / 城市 / 级别 / 薪资**。
- **明确不做：** 新增、修改、删除、详情页；岗位行一律来自已导入 SQL。
- **双出口：** 同一 `t_job` 供页面 schema 列表与 Agent MCP 读取（见 [plan.md § 岗位库双出口](./plan.md#关键决策)）。

### 4.3 分析报告页（custom · 一按钮两板块）

- `moduleType: custom`；**一个「开始分析」按钮 + 两个结果板块：**
  1. **简历画像：** 六维度雷达 + 强弱项文字（每维 0–100，带 rubric 出处与原文证据）。
  2. **岗位推荐：** Top **10** 岗位卡片（从全库 **150–300** 条中，经召回 **4000→400** 再精排得出，见 [plan.md § 召回策略](./plan.md#关键决策)）。
- 结构化 JD 要求：由后续 MCP 从 JD 正文抽取，写入 `zteam.t_job_requirement`（本 Part 只定表职责，抽取逻辑在 MCP 节落地）。

## 5. 产品决策（定死，后面所有节都受它约束）

### 决策 ① — 六个维度写死

| # | 维度 | 分值 |
|---|------|------|
| 1 | 技术深度 | 0–100 |
| 2 | 工程能力 | 0–100 |
| 3 | 业务理解 | 0–100 |
| 4 | 项目影响力 | 0–100 |
| 5 | 协作沟通 | 0–100 |
| 6 | 成长性 | 0–100 |

**硬性要求：** 每个维度的分数 **必须同时挂载**：

1. **rubric 出处**（来自按级别切分的 rubric 知识，见 [plan.md § rubric](./plan.md#关键决策)）；
2. **简历原文证据**（可定位到 `t_resume` 结构化字段或 `data/resumes/` 原文片段）。

不允许「只有分数没有出处」的裸分。

### 决策 ② — 综合分由代码算，不由模型算

- **模型职责：** 只输出 **逐条判定**（维度项是否满足、证据片段、置信度等结构化字段）。
- **权重来源：** 岗位库 `t_job` / `t_job_requirement` 中的级别与权重配置，**禁止写死在业务代码里**。
- **综合分计算：** Java 规则引擎读取判定结果 + 权重，做 **加权求和** → 综合分。
- **必须满足：** 可复现（同输入同输出）、可审计（可追溯每条判定与权重）、可调权（改配置不改代码）。

## 6. 语言分工表

| 语言 | 职责 | 为什么是它 |
|------|------|------------|
| **Python** | 简历文件（PDF/DOCX 等）与 JD 正文 → 结构化字段写入 `t_resume` / `t_job_requirement` | 生态成熟（PyMuPDF、python-docx 等），适合 **离线文档解析** MCP Server；与 Java/Go 解耦 |
| **Java** | 读取岗位表与权重配置，运行规则引擎，输出六维分数与综合分 | 规则引擎（Drools / 自研表驱动）传统强项；**确定性计算** 不放 LLM |
| **Go** | 全库岗位召回（150–300 条 → 粗排 Top 20 → 精排候选 400 条）与证据打包 | 并发与向量/关键词召回性能可控；适合 **高吞吐检索** MCP |
| **Node/TS** | HTTP/SSE 编排、页面、Agent 声明、eval 断言 | 与 elpis 框架同栈；**稳定面合同** 已在 TS 侧，避免跨语言重复实现网关 |

所有外部能力 **一律通过 MCP 声明接入**，框架侧不嵌入语言运行时（见 §7）。

---

## 7. 稳定面（合同）

以下接口与约定 **锁死**，类型集中放在 **`elpis/app/ai/contracts/`**（demo 侧 mirror 同路径约定，见 [plan.md § 先剥合同](./plan.md#关键决策)）：

| 合同项 | 约定 |
|--------|------|
| **HTTP 响应** | 三字段：`ok` · `data` · `error` |
| **SSE 事件** | 三事件：`step` · `delta` · `done` |
| **扫描约定** | Agent / Skill / Prompt / MCP 按目录 glob 自动注册，禁止硬编码第二套发现机制 |
| **Store 接口** | trace / memory / vector 走框架 Store 抽象，Resume Studio 不私有实现第二套存储 |

**页面扩展：** 走已有 **`custom`** 扩展位，**不新增 `moduleType`**。

**数据落库：** 结构化数据 **只落已有 MySQL**（`t_resume` · `t_job` · `t_job_requirement`，库名 **`zteam`**）；**禁止** H2 / sqlite / 第二个库 / 用 json 文件充当库。

**原文件：** `data/resumes/` 仅装上传原件，**不进 git**。

**外部能力：** 一律 MCP 声明接入（Python 解析 · Java 算分 · Go 召回），框架零改动挂载。

## 8. 本 Part 允许改 elpis 的三类事

> 其它缺口 **只记录、不动框架**；完整清单见 [plan.md § 还债](./plan.md#总策略)。

1. **体检瘦身** — 删除 Part3 实验性死代码、重复 Provider、未使用的 eval 分支。
2. **补原语** — 按名互调（invoke-by-name）与并行委派（parallel delegate）原语，供队长 Agent 串并行编排。
3. **目录收敛** — `contracts/` · `agents/` · `skills/` · MCP 配置归位，与扫描约定一致。

---

## 9. 禁止清单

| # | 禁止项 | 原因 |
|---|--------|------|
| 1 | 把业务判断写进框架 | 框架只提供原语与合同，Resume Studio 业务放 demo + MCP |
| 2 | 在框架里再写一套 supervisor 循环 | 队长是普通 Agent 声明，不是第二种运行时 |
| 3 | 给模型 SQL 执行工具 | 确定性读写走 Java MCP / 已有 API |
| 4 | 让模型直接解析 PDF 原文 | 解析走 Python MCP，模型只吃结构化字段 |
| 5 | 让模型输出综合分 | 综合分只许 Java 规则引擎加权求和 |
| 6 | 让模型算「3 年以上经验」等算术 | 年限、阈值比较进规则引擎或 SQL |
| 7 | rubric 整套塞进 system prompt | rubric 按级别检索注入，控制 token 与版本 |
| 8 | 打分结论无 rubric 出处 | 违反决策 ①，不可审计 |
| 9 | 权重写死在代码里 | 违反决策 ②，不可调权 |
| 10 | 简历原文进 git | 隐私；原文件只放 `data/resumes/` |
| 11 | 用 json 文件充当简历库或岗位库 | 违反 §7 单库原则 |
| 12 | 新增 moduleType 或第二套存储 | 违反稳定面 |

## 10. 验收表

> 当堂验证动作见 [tasks.md § 收口验收](./tasks.md#收口验收)；此处 **一节一行**，共 **十二行**。

| 节 | 验收标准（事实陈述） |
|----|----------------------|
| §1 目标 | 用户能在 `war-room` 项目上传一份简历并发起分析，10 分钟内看到报告页 |
| §2 痛点 | 同一份简历重复分析两次，六维分数与综合分完全一致（可复现） |
| §3 边界 | 报告页只有「分析结果 + 推荐」，无在线编辑/代投入口 |
| §4 简历库 | `t_resume` 列表可 CRUD；「分析」按钮可进入报告页 |
| §4 岗位库 | 列表只读展示 150–300 条岗位的标题/公司/城市/级别/薪资，无增删改详情 |
| §5 决策① | 六个维度各 0–100，每条分数可在 UI 展开 rubric 出处 + 简历原文证据 |
| §5 决策② | 修改 `t_job` 权重配置后，综合分变化且无需改代码、无需重训模型 |
| §6 语言 | Python/Java/Go 各 1 个 MCP Server 可被 Agent 调用，Node 侧可见 step 轨迹 |
| §7 合同 | HTTP 仅三字段、SSE 仅三事件；contracts 类型集中在约定目录 |
| §8 框架改动 | elpis 仅含瘦身 + 按名互调/并行委派 + 目录收敛，无业务 if-else |
| §9 禁止 | eval 断言验证：无模型 SQL、无模型 PDF 解析、无模型综合分输出 |
| §10 端到端 | 从简历库点「分析」→ 报告页展示六维雷达 + Top 10 岗位，eval 全绿 |
