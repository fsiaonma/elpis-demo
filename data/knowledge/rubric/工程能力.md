# 工程能力

**这个维度判什么：** 判候选人是否具备可重复、可协作、可上线的工程化习惯——构建发布、质量防护、可观测性、环境一致性与变更风险控制，且能在简历中用具体做法与结果说明。

**这个维度不判什么：** 不判算法多复杂、不判业务域理解深浅；不把「写过单元测试一条」自动等同于工程体系成熟；不根据公司规模推断工程水平。

## 【L1】基础交付——能在指导下完成构建与上线相关操作

能在说明文档或他人协助下完成本地运行、打包与一次性的上线配合，简历中几乎不出现工程化体系关键词或仅泛泛提及。

**行为特征**
- 仅描述「提交代码」「修复 bug」，无 CI、测试、发布流程字样
- 环境相关只写「本地开发」，无 staging/灰度/回滚
- 协作方式为「交给运维发布」且无个人侧检查清单
- 质量保障停留在「自测通过」

**正例片段**

根据组长提供的打包脚本打 test 包，在测试环境验证通过后，由运维在周四窗口发布；发布后在群里跟进 30 分钟无异常即下班。

**反例片段**

「精通 DevOps 全链路，保障系统高可用。」——无具体流水线、指标或个人动作，不能据此给 L2 以上；工程能力按 L1 处理。

**分数区间：** 0–40

## 【L2】常规实践——在单应用内使用常见工程工具

在负责的应用内使用过测试、lint、构建工具或简单脚本中的若干项，能写清常规发布路径，但体系未覆盖多环境或多团队协作。

**行为特征**
- 提到 ESLint/Jest/Webpack/Vite/Maven 等之一，并对应到日常开发
- 有「提 PR」「Code Review」但无质量门禁描述
- 发布为「测试通过后上线」，无灰度比例或自动化回滚
- 日志/监控仅「看 Kibana」类被动表述

**正例片段**

项目使用 GitLab CI 跑 lint + 单元测试（覆盖率约 45%）；合并 master 后自动打 Docker 镜像，测试环境由 Jenkins 拉取部署；线上问题通过 Sentry 告警邮件定位。

**反例片段**

「使用 Docker 容器化部署。」——若只有一句且无镜像构建责任、无环境差异说明，不足以判 L3；最多 L2 下限。

**分数区间：** 41–58

## 【L3】应用级工程负责人——建立或维护一条完整交付链路

对单个应用或一条服务线建立从提交到生产的可重复流程，含质量门禁、版本策略与基本可观测性，简历可核对环节与个人职责。

**行为特征**
- 写清 CI 阶段（lint/test/build）及失败是否阻断合并
- 有分支策略或发布节奏（如 release 分支、每周火车）
- 线上有日志规范、链路 ID 或指标 dashboard 中至少一项
- 个人角色为「搭建」「维护」「制定规范」之一

**正例片段**

2023 年起负责支付回调服务的工程化：GitHub Actions 阻断覆盖率 <60% 的 PR；staging 与 prod 配置分离（环境变量 + 密钥托管）；上线 checklist 含 DB migration 顺序与回滚 SQL；接入 Prometheus 后 5xx 率异常 5 分钟内告警到 on-call。

**反例片段**

「参与制定公司研发规范。」——无个人负责的应用或链路，不能给 L3；待校对：若仅为委员会成员且无落地应用名，按 L2。

**分数区间：** 59–72

## 【L4】跨应用/跨团队工程治理——度量驱动改进且有对照结果

推动多个应用或团队统一工程标准（构建、测试、发布或观测），并有前后对比数据或故障/效率类量化结果。

**行为特征**
- 影响面 ≥2 个团队或 ≥3 个仓库/服务
- 有统一模板、平台或内部工具被他人使用
- 结果含发布频率、MTTR、变更失败率、构建耗时等至少一项可核对指标
- 个人为方案推动者而不仅是使用者

**正例片段**

主导前端 7 个 SPA 接入统一 CI 模板（共享 GitHub Actions reusable workflow）：2024 H1 构建时间中位数从 11min 降到 4min；生产回滚次数从月均 3 次降到 0.5 次（变更记录统计）；编写发布 Runbook 供各组 on-call 共用。

**反例片段**

「推动敏捷转型，提升交付效率。」——无工程链路、无指标，不属于工程能力 L4；最多 L2。

**分数区间：** 73–88

## 【L5】组织级工程体系——标准/platform 成为默认路径

定义或运营公司级工程平台/规范，新业务默认接入，离职或换组后仍持续运行，简历有 adoption 与生命周期证据。

**行为特征**
- 平台或规范名称 + 接入团队/应用数量
- 有版本演进、迁移计划或废弃旧流程的记录
- 与稳定性/安全合规有明确挂钩（审计、等保、SOC2 等择一可核对）
- 个人为 Owner 或架构组明确负责人

**正例片段**

从 0 搭建内部 IDP（Backstage + 自研脚手架），2022–2025 成为后端 80+ 服务创建的唯一入口；统一 golden path 含 OTel 埋点、SBOM 扫描与金丝雀发布；2024 年变更相关 P0 事故较 2021 基线减少 60%（SRE 年报口径）。

**反例片段**

「熟悉 CI/CD 最佳实践，多次分享。」——分享不构成组织级体系，工程能力 L5 不成立；待校对：若有平台 Owner 头衔但无 adoption 数字，最高 L4。

**分数区间：** 89–100

## 常见误判

1. **把会用的工具当建立的体系：** 个人会用 Jenkins 不等于 L3，需写清是否为该应用/团队链路的责任人。
2. **把测试覆盖率单一数字当 L4：** 覆盖率 80% 但无发布、观测、跨团队推广，通常停在 L3。
3. **把运维岗位默认高工程分：** 若简历只写「维护服务器」而无变更管理、自动化与度量，工程能力可能仅 L1–L2。
