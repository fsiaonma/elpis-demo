# 技术深度

**这个维度判什么：** 判候选人在具体技术问题上能独立决策到哪一层——是照方案写代码，还是能讲清模块内外的取舍、推动改造，乃至让别人沿用其技术方案。依据只能是简历里写明的技术职责、设计动作与结果描述。

**这个维度不判什么：** 不判业务好不好、项目响不响亮、用了多少种技术名词；不判「是否大厂」「是否名校」；不把团队整体成果默认算到个人头上，除非简历写清个人在设计或决策中的角色。

## 【L1】执行层——按需求实现功能，技术选型由他人决定

按需求实现功能，技术选型由他人决定；个人负责编码、联调与缺陷修复，不承担模块级方案选择。

**行为特征**
- 职责描述以「参与开发」「按设计实现」「完成分配任务」为主
- 技术栈列表有，但缺少「为何选用」「对比过何种方案」类表述
- 问题处理停留在功能点或单接口，未出现模块边界或系统间接口的设计叙述
- 未写清个人在方案阶段的输入，只写执行结果

**正例片段**

2022.03–2023.08｜某电商公司｜前端开发  
负责活动页与商品详情页开发，按 PRD 与 UI 稿使用 Vue2 + Element 实现；配合后端联调下单接口，修复 IE11 兼容问题；单元测试覆盖核心业务组件。

**反例片段**

「深度参与公司核心交易链路重构，技术选型 Vue3 + Pinia，性能提升 40%。」——若全文未说明个人负责的是哪一段设计或决策、40% 相对何基线，不能据此给到 L3 及以上；最多视为参与执行或信息不足，按 L1–L2 区间从严判。

**分数区间：** 0–40

## 【L2】模块内熟练——能在给定边界内做小范围技术判断

在单个功能或组件范围内，能完成常规实现并处理常见技术问题，偶有小范围实现方式选择，但未承担模块级方案责任。

**行为特征**
- 能写清自己负责的功能模块名称与交付物
- 出现「优化」「重构」但范围限定在组件、页面或单一服务内
- 有具体技术点（如懒加载、缓存、防抖）与对应场景，无系统级改造叙述
- 技术选型仍表现为「采用团队统一栈」或「沿用现有架构」

**正例片段**

独立负责订单列表页：封装虚拟滚动表格组件，将 5000 条 mock 数据下首屏渲染从 3.2s 降到 0.8s（Chrome 96，本地 profiling）；列表筛选与 URL query 同步，便于运营分享链接。

**反例片段**

「熟悉微服务、分布式、高并发，有丰富中间件经验。」——仅为技能或关键词堆叠，无模块内具体设计或度量，不能判为 L2 的技术深度上限以上；按无有效深度证据处理，倾向 L1。

**分数区间：** 41–58

## 【L3】模块级设计者——能独立完成模块级设计并讲清取舍

能独立完成一个模块（含前后端边界清晰的一块能力）的方案设计，在简历中可核对：备选方案、选型理由、权衡点与落地结果。

**行为特征**
- 明确写出模块职责边界（输入输出、依赖方、失败策略至少其二）
- 有「对比 A/B」「最终选用…因为…」或等价可审计表述
- 设计结果对应可定位的代码范围或文档产出（设计 doc、RFC 名称等）
- 改造影响范围通常在一个应用或一条业务线内，未写跨多系统主导

**正例片段**

负责商家对账模块：在「每晚批处理对账文件」与「事件驱动逐笔核对」之间选型，因日单量 <20 万且财务要求 T+1 报表，选用批处理 + 幂等表方案；定义与支付、清结算三个下游的 idempotent key 规则，联调期将重复入账问题从日均 12 起降到 0。

**反例片段**

「作为核心开发参与中台建设，深度使用 Spring Cloud。」——「参与」「使用」未构成模块级设计证据；若无个人负责的子模块与取舍描述，不应给 L3，按 L2 或以下。

**分数区间：** 59–72

## 【L4】跨团队/跨系统改造主导——有可量化的技术改造结果

主导过跨团队或跨系统的技术改造（非单一模块内部重构），简历中同时存在：主导角色、改造范围、至少一项可量化或可对照基线的结果。

**行为特征**
- 角色为「主导」「负责整体方案」「担任技术 Owner」等可对应到改造链路
- 改造涉及两个及以上团队或两个及以上系统/服务边界
- 结果含数字或前后对照（延迟、错误率、人力、发布频率等）且基线可理解
- 有落地周期或里程碑，非仅规划阶段

**正例片段**

2023 起主导订单读链路从单体 DB 只读副本迁移至独立查询服务：协调交易、库存、会员三个团队接口契约；灰度 6 周，大促期间 P99 从 420ms 降至 180ms（同流量对比 618 前一周），读库 CPU 峰值下降 35%。

**反例片段**

「优化系统架构，大幅提升性能与稳定性。」——无跨系统范围、无个人主导表述、无基线数字，不得给 L4；项目影响力维度亦不能单靠此句抬高，技术深度最高按 L2 处理。

**分数区间：** 73–88

## 【L5】技术方向定义者——方案被组织或社区广泛沿用

在公司或社区范围内定义过技术方向（标准、框架、平台或方法论），他人按该方案实施或引用，简历中有可核对的影响面描述。

**行为特征**
- 产出物为规范、平台、开源项目维护、公司级技术雷达/架构标准等
- 明确 Adoption：多团队采用、内部培训次数、外部 star/下载、会议分享被引用等至少一项
- 个人角色为发起人或主要维护者，非「成员之一」
- 时间跨度通常跨季度以上，非一次性分享

**正例片段**

发起并维护公司前端 Monorepo 与构建规范（基于 pnpm + Turborepo），2022–2024 推广至 9 个业务线、约 40 个应用统一接入；对内编写《模块联邦接入指南》作为唯一准入文档，新人接入周期从 2 周缩短到 4 天（HR  onboarding 统计，2023 Q4）。

**反例片段**

「在公司内部分享 React 最佳实践，获得好评。」——单次分享不构成方向定义；无持续采纳与标准约束力，技术深度通常不超过 L3–L4 边界，此处判 L3 封顶待具体采纳证据补充。

**分数区间：** 89–100

## 常见误判

1. **把技术栈数量当深度：** 列出十几项中间件但无任何设计或取舍叙述，最多 L1–L2，不能因「看起来厉害」给 L3。
2. **把团队项目默认算个人主导：** 「参与核心系统」无个人边界时，技术深度应从 L2 起评，需额外证据才能升到 L3。
3. **把性能数字无基线当 L4：** 仅有「提升 50%」而无对比对象或测量条件，技术深度与项目影响力均不应超过 L2 对应区间上限。
